# Переход с fixed window на честный token bucket

## Проблема

Текущая реализация `RateLimiter` (ratelimiter.go) — это fixed window
счётчик, несмотря на то что в комментарии к типу заявлен token bucket:

- Счётчик `requests` сбрасывается в 0 раз в `interval`, когда истекает
  `retryAfter`.
- Между сбросами лимит держится честно (не больше `rps` за `interval`),
  но **на границе окна возможен всплеск**: `rps` запросов в конце
  одного окна + `rps` запросов сразу после сброса в начале следующего
  — итого до `2*rps` запросов за время значительно меньше `interval`.
- В реальном использовании (`clientUpdateStocks`) `AllowRequest()`
  вызывается параллельно из множества горутин на каждый батч, поэтому
  всплеск на границе окна легко может уложиться в доли секунды и
  превысить honest sliding-window лимит на стороне внешнего API (Ozon
  считает лимит ~50 rps как скользящее окно в 1 секунду).

## Решение: честный token bucket

Заменить fixed-window логику на классический token bucket с непрерывным
пополнением токенов:

- Состояние: `tokens float64` (текущее количество доступных токенов) и
  `lastRefill time.Time` (момент последнего пересчёта).
  Ёмкость бакета — `capacity` (по умолчанию равна `rps`, задаётся как
  максимальный размер всплеска, разрешённого клиенту).
- Скорость пополнения: `rate = rps / interval` токенов в единицу
  времени (float64, наносекунды как база для точности).
- При каждом вызове `AllowRequest()`:
  1. `elapsed := now.Sub(lastRefill)`
  2. `tokens = min(capacity, tokens + elapsed * rate)`
  3. `lastRefill = now`
  4. если `tokens >= 1` — списать 1 токен, вернуть `true`
  5. иначе вернуть `false`
- Такой подход гарантирует, что за любое скользящее окно длиной
  `interval` не будет выдано больше `rps` разрешений (плюс не более
  `capacity - rps` токенов первоначального запаса, если бакет не был
  пуст) — без резких скачков на границах.

## Изменения публичного API

- `NewRateLimiter(rps int, interval time.Duration) *RateLimiter` —
  сигнатура не меняется.
- `AllowRequest() bool` — поведение не меняется с точки зрения
  контракта (true/false), меняется внутренняя механика.
- `CurrentState() (int, time.Duration)` — переосмыслить под token
  bucket:
  - первое значение: `int(tokens)` — сколько целых токенов доступно
    сейчас;
  - второе значение: расчётное время до следующего доступного токена
    (0, если токены уже есть).
- `GetRetryAfter() time.Time` — либо оставить как "время, когда будет
  доступен следующий токен" (по аналогии с CurrentState), либо
  удалить, если станет неактуальным. Требует решения при реализации,
  т.к. текущий тест на это опирается.

## Что нужно обновить

1. `ratelimiter.go` — реализация (структура, `NewRateLimiter`,
   `AllowRequest`, `CurrentState`, `GetRetryAfter`, комментарии).
2. `ratelimiter_test.go` — тесты, завязанные на fixed-window семантику
   (например `TestRateLimiter_ResetBehavior`, `TestAllowRequest_ResetAfterInterval`,
   `TestCurrentState`), переписать под token-bucket поведение.
   `TestConcurrentAccess` (200 горутин, ожидание ровно 100 allowed) —
   проверить, остаётся ли инвариант справедливым при непрерывном
   пополнении (в момент старта бакет полон — да, останется).
3. `example_test.go` — примеры, где показан сброс через `time.Sleep`
   и ожидаемый `Output`, тоже завязаны на fixed-window тайминги —
   актуализировать под token-bucket тайминги (пополнение конкретного
   количества токенов за конкретное время).
4. Комментарий к пакету/типу — убрать несоответствие "token bucket" в
   описании и реальным поведением (после рефакторинга комментарий
   станет верным).

## Обратная совместимость

Публичная сигнатура не меняется. Поведение `AllowRequest` вблизи
границ интервалов изменится (это и есть цель фикса), поэтому тесты и
примеры, точно завязанные на fixed-window тайминги, потребуют
пересмотра значений/ожиданий, а не просто косметики.
